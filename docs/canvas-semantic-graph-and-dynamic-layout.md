# 画布语义编排与动态布局设计

## 1. 文档状态

- 状态：方案已定稿，可进入开发
- 目标：画布默认只展示主干节点，展开时动态重新布局并收紧空白
- 适用范围：Canvas 节点、结构关系、展开/收起、自动布局、用户手动调整

## 2. 背景

当前系统由 Agent 同时负责两类工作：

1. 创建节点并确定节点之间的语义关系；
2. 指定 `position_x`、`position_y`、`layer`，并根据布局诊断反复移动节点。

前端已经负责连接点选择、路径绘制、标签避让、折叠隐藏和部分连线诊断，但不会自动重新排列节点。因此，当节点数量增长时存在以下问题：

- Agent 需要消耗额外工具调用处理像素级布局；
- 坐标容易受节点尺寸、窗口尺寸和当前展开状态影响，Agent 无法可靠判断；
- 默认加载全部节点导致画布密集，用户难以快速理解主干结构；
- 收起节点后只隐藏内容，剩余节点不会自动收拢，画布仍然存在空洞；
- 前端靠自然语言字符串（`"contains"` / `"包含"`）判断父子关系，与后端已有的类型判据不一致。

## 3. 总体目标

将系统职责调整为：

- Agent 负责完整语义图：创建节点、建立关系；
- 前端负责当前视图：决定哪些节点可见，并对可见节点动态布局和绘制连线；
- 默认不展示全部节点，只展示足以理解作品主干的层级；
- 用户展开或收起节点时，重新计算可见子图并以动画调整布局；
- 用户操作期间保持视觉焦点稳定，不因全局重排而迷失位置。

核心数据流：

```text
完整语义图（全部节点和关系）
          ↓
根据展开状态生成可见子图
          ↓
仅对可见子图计算节点布局
          ↓
计算连接点、路径与标签位置
          ↓
React Flow 渲染和动画过渡
```

## 4. 非目标

本期不包含：

- 由 Agent 指定精确像素坐标；
- 一次性解决任意复杂图的全局最优布局；
- 将所有非结构关联线始终展示在主画布；
- 新增数据库字段或执行数据迁移；
- 删除现有节点坐标字段或破坏旧作品兼容性；
- 多种可切换布局视图；
- 展开状态的持久化与多端同步；
- 用户手动调整同级顺序。

## 5. 核心概念

### 5.1 完整语义图

后端保存作品的全部节点和关系，不受前端展开状态影响。隐藏节点仍然存在于完整语义图中，也可以被搜索、被 Agent 查询或更新。

### 5.2 可见子图

前端根据以下输入，从完整语义图中投影出当前需要展示的节点和关系：

- 结构根节点集合；
- `expandedNodeIds`；
- 当前聚焦或搜索命中的节点；
- 默认展开深度。

隐藏必须是投影结果，不能从前端的完整数据集合中删除节点。

### 5.3 关系类别由节点类型派生，不新增字段

关系类别描述节点为什么相关；视觉连线描述该关系当前如何画出来。二者必须分离。

关键决策：**关系类别是从节点类型推导出的派生值，不作为字段存储。** 理由是节点类型已经提供了这一能力：

- `validate_node_type` 将类型强校验为 7 个固定枚举值，不允许 Agent 自创；
- 层级链是固定顺序 `outline → volume → plot → chapter`；
- 后端 `edge_layout_service.HIERARCHY_CHAIN_TYPES` 已经在用这套判据。

若额外在边上存一个结构字段，同一事实会存在两处，出现冲突时还需要再写一套仲裁逻辑，收益为零。

判定规则（`relationKind` 为派生值）：

| 条件 | relationKind | 是否影响主布局 |
| --- | --- | --- |
| 两端均为层级链类型，且 target 层级 = source 层级 + 1 | `hierarchy` | 是，形成树或森林 |
| 两端为同一种层级链类型 | `sequence` | 否，仅表示同级先后 |
| 其余合法边（如 `character → chapter`） | `reference` | 否 |
| 两端均为层级链类型但跨越多级 | 非法 | 创建时拒绝 |

层级序号定义：

```text
outline = 0, volume = 1, plot = 2, chapter = 3
```

必须注意的陷阱：`chapter → chapter` 的边两端都属于层级链类型，若只用"两端都在层级链集合内"作为判据，会把前一章误判为后一章的父节点，导致树深度错乱。这类边在系统中真实存在（`EDGE_CONNECTION_RULES_TEXT` 为其定义了固定连线方向），因此判据必须收紧为"严格降一级"，同类型之间一律归入 `sequence`。

现有 `edge_type` 保留为面向用户的自然语言，例如"包含""角色登场""伏笔埋设"。前端和后端不得依赖自然语言文本判断结构关系。`frontend/src/lib/canvasCollapse.js` 中的 `CONTAINS_EDGE_TYPES` 字符串集合应予删除。

遇到不符合上述任何一条的边时必须报错，不得静默降级为 `reference` 后继续渲染，否则结构错误会被布局掩盖而难以定位。

### 5.4 同级顺序复用现有排序函数

不新增 `order` 字段。`Node` 表没有顺序列，但章节顺序已有现成纯函数 `chapter_history_service.chapter_order_key`，其优先级为：

1. `extra_data` 中的 `chapter_number` / `chapter_index` / `order` / `sequence`；
2. 标题中的"第 N 章"数字；
3. `layer`、`position_x`、`created_at`。

前端实现一份等价的排序键函数，同样适用于 `volume` 和 `plot`（标题数字优先，退到创建时间）。

已知副作用：第 3 档回退使用 `position_x`。当 Agent 不再写坐标后该档会退化为仅按 `created_at` 排序。结果仍然确定，但如果后续需要支持用户手动拖拽调整同级顺序，那时才需要引入独立的 `sort_order` 字段——在没有对应交互入口之前提前加字段没有意义。

### 5.5 视图状态

视图状态不属于小说语义。当前 `Canvas.jsx` 的展开状态仅保存在内存：

```js
const [collapsedNodeIds, setCollapsedNodeIds] = useState(() => new Set());
```

本期将其语义反转为 `expandedNodeIds`（默认收起，显式记录展开的节点）。由于当前没有 `localStorage` 或后端持久化，这次反转**不涉及任何数据兼容处理**。

后续若增加持久化，必须为视图状态附带版本号，读到旧版本直接丢弃并按当前默认深度重新初始化——旧的空 `collapsedNodeIds` 表示"全部展开"，新的空 `expandedNodeIds` 表示"全部收起"，两者不可混用。视图状态不得写入 Node 语义字段。

## 6. 功能需求

### 6.1 默认可见范围

首次打开作品时不显示全部节点。默认策略：

- 显示所有结构根节点（没有 hierarchy 父边的层级链节点）；
- 显示根节点的第一层子节点；
- 更深层节点默认隐藏；
- 当前搜索命中、正在编辑或由外部导航定位的节点必须可见，并自动展开其祖先链。

默认深度为可配置常量，后续可升级为作品级设置。

### 6.2 孤立节点不进入画布

这一条直接决定"紧凑"目标能否达成，必须明确实现。

`node_types.py` 规定 `scope=global` 的节点（`worldbuilding`、`note` 以及主角 `character`）**禁止任何连线**，它们在图中完全孤立、没有任何边。若沿用"没有父边即为根节点"的判据，这批节点会全部默认显示。一部长篇作品累积数十条世界观与笔记是常态，届时即便层级链收得再干净，画布依然铺满孤立卡片，紧凑效果完全落空。

方案：

- `worldbuilding`、`note`、主角 `character` 默认不渲染到画布；
- 侧边栏提供按类型分组的聚合入口，显示各类型条目数量，点开为列表；
- 从列表点击条目时打开详情抽屉，不改变画布布局；
- 非主角 `character`（`major` / `minor` / `temp`）有关联边，按 6.6 的关系显示策略处理，不参与树布局。

同时需要修改 `NODE_LAYOUT_RULES_TEXT`：其中"character 位于画布左侧，纵向排列""note、worldbuilding 位于画布左侧"以及"前端不会自动重排"等表述在前端接管布局后全部失效，必须移除。

### 6.3 展开节点

当用户展开具有隐藏后代的节点时：

1. 将该节点加入 `expandedNodeIds`；
2. 显示其直接子节点，不递归展开全部后代；
3. 生成新的可见节点和可见结构边；
4. 重新计算当前可见子图的布局；
5. 以动画将旧位置过渡到新位置；
6. 保持被点击节点的屏幕位置不变（见 6.7 的 anchor 补偿）；
7. 不执行全局 `fitView`。若新增子节点落在视口外，仅在 anchor 补偿完成后做一次小幅平移，且该平移不得抵消 anchor 补偿。

### 6.4 收起节点

当用户收起节点时：

1. 从 `expandedNodeIds` 移除该节点；
2. 隐藏其所有可见后代；
3. 后代从画布淡出；
4. 剩余节点重新布局并收拢空白；
5. 焦点回到被收起的父节点；
6. 保留后代自身的展开状态，以便再次展开时恢复。

### 6.5 隐藏内容提示

有隐藏后代的节点必须显示明确的可发现性提示：

- 展开/收起图标；
- 直接子节点数量；
- 隐藏后代总数；
- 按类型聚合的摘要，例如"3 个情节 · 12 章"。

节点没有 hierarchy 子节点时，不显示展开控件。

### 6.6 非结构关系的显示策略

默认主视图只持续显示 `hierarchy` 边。其他关系按需显示：

- 选中节点时显示与该节点直接相关的 `reference` 和 `sequence` 边；
- 指向隐藏节点的关系不绘制到不可见端点，本期直接隐藏；
- 本期不实现聚合代理边。

### 6.7 动态布局

布局必须以当前可见子图为输入，而不是先布局全部节点再隐藏部分节点。

主布局采用自上而下的树状结构：

- 深度决定 Y 坐标；
- 同级顺序由 5.4 的排序键决定；
- 子树占用宽度决定 X 坐标；
- 父节点位于其可见直接子节点的水平中心；
- 节点间距使用实际节点尺寸计算，复用现有 `nodeDimensions.js`；
- 多个根节点构成森林，根子树之间保留额外间距。

纯函数接口：

```js
layoutVisibleGraph({
  nodes,
  edges,
  previousPositions,
  anchorNodeId,
  direction: "TB",
})
```

布局完成后整体平移结果，使 `anchorNodeId` 的新画布坐标与旧坐标一致，从而维持用户的视觉锚点。

### 6.8 手动拖动与固定

树内节点的位置完全由布局函数推导。本期简化处理：

- 层级链节点不支持手动拖动改变布局位置，拖动后回到计算位置；
- 不引入 pinned 概念。原文档中"pinned 节点尽量保持不动"与"位置由子树宽度推导"在同一次布局内互斥，"尽量"二字会把决策推给实现者，因此本期不做；
- `locked` 字段保留其现有的内容保护语义，不参与布局；
- Agent 不得修改 `locked` 或坐标。

混合布局（部分节点固定、其余自动排布）留待后续版本，届时需要先明确定义冲突解决规则。

## 7. 数据模型方案

**本期不新增字段、不执行数据库迁移。**

保留现状：

- Node 的 `position_x`、`position_y`、`layer`、`locked`；
- Edge 的 `edge_type`、`label`、`extra_data`；
- 旧快照中的坐标字段。

原方案曾建议将结构元数据写入 `Edge.extra_data`（JSON）。该方案已废弃，原因有两点：一是 `relation_kind` 与 `order` 均可由现有信息派生（见 5.3、5.4），本身没有必要存储；二是这两个字段正是需要施加索引与数据库约束的高频结构字段，放入 JSON 列会使所有校验退化为纯应用层逻辑。

### 7.1 树结构约束

后端在创建或更新边时必须校验（当前 `routers/edge.py` 中这些校验**全部缺失**）：

- source 与 target 不能相同；
- 层级链两端必须严格降一级，跨级连接（如 `outline → chapter`）被拒绝；
- 每个节点最多只能有一个 hierarchy 父节点；
- 新的 hierarchy 关系不能形成环；
- 删除父节点时沿用现有节点删除语义，不自动删除子节点。

单父与无环并非可选项：它们是树布局正确性的前提。若同一个 `plot` 被两个 `volume` 连接，可见子图投影与布局结果都将变为不确定，表现为节点位置随机跳动。

父子类型规则：

```text
outline → volume
volume  → plot
plot    → chapter
```

### 7.2 已废弃概念

`element` 已不再是节点类型。`validate_edge_endpoints` 明确拒绝 element 端点的连线，章节元素改为存放在 `chapter.extra_data.chapter_elements`。因此 `canvasCollapse.js` 中的 `buildElementChapterLinks`、`isElementHiddenByCollapsedChapters` 及相关跨章复用可见性逻辑属于历史遗留，迁移时直接删除。

## 8. Agent 方案

### 8.1 工具输入调整

`create_node` 和 `batch_create_nodes`：

- `position_x`、`position_y` 改为可选并从工具描述中淡出；
- Agent 创建节点时不再传坐标；
- `layer` 不再表示像素布局层，由 hierarchy 深度推导；
- 字段暂时保留以兼容现有 API。

`create_edge` 和 `batch_create_edges`：

- 不新增参数；
- `edge_type` 继续承载自然语言关系名称；
- 工具返回结构校验错误（跨级、多父、成环），不再返回要求 Agent 修复坐标的布局警告。

### 8.2 删除 Agent 布局职责

完成前端自动布局后，移除：

- 节点重叠检测反馈；
- 要求 Agent 调整坐标直至 warnings 清零的提示；
- Agent 根据前端连线诊断再次移动节点的流程；
- `NODE_LAYOUT_RULES_TEXT` 及 Supervisor 提示词中关于像素间距和坐标规划的内容；
- `backend/services/agents/node_layout.py` 中面向 Agent 的布局计算。

## 9. 前端方案

### 9.1 状态拆分

当前 `Canvas.jsx` 第 118 行的 `useNodesState` 同时承担完整数据与显示数据，必须拆分：

```js
const [allNodes, setAllNodes] = useState([]);
const [allEdges, setAllEdges] = useState([]);
const [expandedNodeIds, setExpandedNodeIds] = useState(new Set());
```

通过 `useMemo` 依次得到：

```js
const visibleGraph = projectVisibleGraph(...);
const layoutedNodes = layoutVisibleGraph(...);
const displayEdges = routeVisibleEdges(...);
```

若继续使用 `useNodesState`，必须明确该 state 只保存渲染节点，完整节点另存，避免隐藏节点被误认为已删除。

### 9.2 新增模块

```text
frontend/src/lib/canvasRelation.js    关系类别派生与层级序号
frontend/src/lib/canvasGraph.js       父子索引、根节点、祖先链、子树统计、环检测
frontend/src/lib/canvasVisibility.js  根据展开状态生成可见子图
frontend/src/lib/canvasLayout.js      对可见子图计算坐标
frontend/src/lib/canvasOrder.js       同级排序键（对应 chapter_order_key）
```

`canvasCollapse.js` 的 contains 字符串判断与 element 逻辑迁移完成后删除。

### 9.3 可见子图算法

```text
visible = 结构根节点
for each visible node:
    if node is expanded:
        visible += direct hierarchy children

if focus/search target exists:
    visible += target
    visible += all hierarchy ancestors of target
```

可见结构边为两个端点均可见的 hierarchy 边。`sequence` 与 `reference` 边依据 6.6 的显示策略单独过滤。

### 9.4 布局稳定性

- 所有遍历使用 5.4 的确定性排序键；
- 保留上一次可见节点坐标作为布局输入；
- 使用被操作节点作为 anchor 做整体坐标补偿；
- 布局期间合并短时间内的多次展开操作，避免竞态；
- React Flow 节点使用 CSS transform transition 过渡。

### 9.5 数据刷新

Agent 创建或更新节点后：

- 刷新完整语义图；
- 不自动展开新增节点；
- 新增节点属于已展开父节点时，显示并重新布局；
- 父节点未展开时，仅更新其隐藏数量提示；
- Agent 操作直接响应用户"创建并打开某章节"时，事件可携带 `focus_node_id`，前端自动展开祖先链并定位。

## 10. 后端方案

后端保障语义结构，不计算视图坐标：

- 在 `routers/edge.py` 增加 7.1 的全部校验；
- 关系类别判定逻辑与前端保持一致，建议由后端提供工具函数并在响应中携带派生结果，避免两端实现漂移；
- 查询节点时继续返回完整节点与完整边；
- 布局诊断不再作为要求 Agent 继续行动的反馈。

首期沿用当前 nodes/edges 接口，不新增 API。

## 11. 撤销与快照

现有画布快照包含坐标，迁移期间保持兼容：

- 第一阶段保留现有快照结构；
- 语义撤销：恢复节点、内容和关系；
- 自动布局产生的纯视觉坐标变化不压入语义撤销栈；
- 展开与收起操作不进入作品内容撤销栈；
- 恢复旧快照后，先恢复语义图，再按当前展开状态重新布局，忽略快照中的坐标。

## 12. 开发阶段

### 阶段一：关系判定与结构校验（无数据迁移）

- 实现关系类别派生函数，含"严格降一级"判据与 `chapter → chapter` 的 sequence 归类；

## 13. 测试方案

### 13.1 关系判定单元测试

- `volume → plot` 判为 hierarchy；
- `chapter → chapter` 判为 sequence，不产生父子关系；
- `volume → volume` 判为 sequence；
- `outline → chapter` 判为非法并拒绝；
- `character → chapter` 判为 reference；
- 自然语言 `edge_type` 为"包含"但类型不构成降级时，不判为 hierarchy；
- 非法结构报错而非降级为 reference。

## 14. 验收标准

1. Agent 创建结构节点时不再需要提供像素坐标；
2. 父子关系由节点类型判定，不依赖"包含"等自然语言，且 `chapter → chapter` 不被误判为父子；
3. 首次打开作品时不默认渲染全部节点，孤立节点不占用画布空间；
4. 用户可以逐层展开和收起结构节点；
5. 每次展开或收起后，仅针对可见子图重新布局；
6. 重新布局后可见节点间距满足最小间距常量，画布不保留隐藏节点空洞；
7. 被操作节点在屏幕中的位置保持稳定；
8. 隐藏节点仍保留在完整数据中，可被搜索和 Agent 更新；
9. 旧作品和旧快照能够正常加载；
10. Agent 不再进入"布局警告—移动节点—再次诊断"的循环；
11. 全程未新增数据库字段、未执行数据迁移。

## 15. 关键决策摘要

- 隐藏节点不是删除节点，而是从完整图投影出当前可见子图；
- 布局输入必须是可见子图，不能先布局全部节点再隐藏；
- 关系类别由节点类型派生，不新增 `relation_kind` 字段，不使用 JSON 列存储结构元数据；
- 层级判据必须是"严格降一级"，同类型之间归为 sequence，否则 `chapter → chapter` 会破坏树结构；
- 同级顺序复用 `chapter_order_key` 的回退链，不新增 `sort_order` 字段；
- 单父与无环校验是树布局的前提，当前后端完全缺失，必须补齐；
- 孤立节点（worldbuilding / note / 主角）默认不进画布，否则紧凑目标无法达成；
- Agent 输出语义结构，不输出像素坐标；
- 展开状态属于用户视图，不属于小说语义，本期不持久化；
- 动态布局必须维持操作节点的视觉锚点；
- 本期不引入 pinned，避免与树布局产生未定义的冲突。
